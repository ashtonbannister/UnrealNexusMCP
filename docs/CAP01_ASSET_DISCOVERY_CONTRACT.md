# CAP-01 asset discovery: source comparison and proposed snapshot contract

Status: **source/design only**. No provider has been selected, no new Nexus operation has been exposed, no compatibility patch has been implemented, and no native behavior has been qualified. The [CAP-01 register](CAPABILITY_BACKLOG.md#cap-01) and canonical catalog remain authoritative. This analysis covers a possible narrow asset-listing child contract, not actor discovery, graph reads, asset inspection, or the whole CAP-01 family.

## Required distinction

An exact asset discovery response must identify each returned object, report its scope and any incomplete indexing, bound work and response sizes, and avoid presenting pages assembled across changed registry state as one consistent snapshot. It must not turn absence from an incomplete Asset Registry into proof an asset does not exist. Exact identity at discovery time also cannot prove that an asset still exists or is unchanged when a later operation dispatches: that operation needs its own live validation and, where semantics require it, a checked revision/identity precondition.

## Pinned candidates examined

### UE-MCP `asset.list` / `list_assets`

The [pinned listing handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Asset/AssetHandlers.cpp#L1323-L1459) calls `GetAssets`, materializes and sorts all matching results and then cuts a page. A page limit bounds row count in the emitted asset array, not registry enumeration, sort, memory, string lengths, or bytes. The returned `path` is a package name and `name` is a separate field; the object-path value used as the cursor anchor is not itself returned as the row's exact identity. Do not assume concatenation reproduces every native object path without reviewing and validating Unreal's object-path semantics.

The [pagination helper](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Public/HandlerPagination.h#L291-L415) resumes by searching the current enumeration for an anchor. It reports changes when that anchor moves or disappears, but returns early when the anchor stays at the same index. Additions or deletions after the anchor, or substitutions before it that leave its index unchanged, can therefore go unreported; even a different total is not checked on that early-return path. Missing anchors also produce an offset-based page annotated as changed rather than a refusal. A cursor is a query-bound continuation hint, not a frozen collection or an authenticated capability.

### EngineWire `manage_asset.list`

The [pinned catalog record](https://github.com/ChiR24/Unreal_mcp/blob/5a17d6d343ef9b40a509068cff73f1bfb4509815/src/tools/catalog/capabilities/records/manage-asset/asset-lifecycle.ts#L12-L27) describes paginated output; the [native handler](https://github.com/ChiR24/Unreal_mcp/blob/5a17d6d343ef9b40a509068cff73f1bfb4509815/plugins/EngineWire/Source/EngineWire/Private/Domains/AssetWorkflow/Operations/McpAssetListing.cpp#L128-L252) materializes and sorts all matched assets, cuts an offset page and separately enumerates folders without the asset page limit. Its returned asset path comes from a soft object path, which is more directly useful as an object identity than UE-MCP's package-only `path`. The handler explicitly says assets not yet indexed by background scanning may be absent.

The cursor's [revision](https://github.com/ChiR24/Unreal_mcp/blob/5a17d6d343ef9b40a509068cff73f1bfb4509815/plugins/EngineWire/Source/EngineWire/Private/Domains/AssetWorkflow/Operations/EngineWireAssetListCursor.h#L11-L32) is one process-static generated GUID. It detects a different process/session but is not updated when the Asset Registry changes. Consequently a same-session insert/delete or rename can shift offset pages without invalidating the cursor. Path binding does not by itself bind every filter. No inference is made about other providers or a later upstream revision.

Neither reviewed pinned implementation establishes the full contract above. A wrapper may preserve a provider's honest weaker continuation semantics, but must not call it an exact consistent snapshot, silently omit folders, or claim bounded native work merely because a response page is small. In particular, post-receipt truncation in Node cannot undo native work, recover a dropped result or prove no rows were missed. No route is admitted by this document.

## Candidate native design for independent review

A new, source-locked compatibility delta or a different independently reviewed provider would be needed. This is a design candidate, not a claim that Unreal offers the necessary atomic enumeration primitives on every engine version.

1. A fixed read-only start operation accepts a canonical, explicit allowed content root, bounded simple filters, recursion policy and a host-configured upper bound. It excludes tags, file metadata and folder enumeration unless each has its own bounded schema. It returns exact object path and class path, not an inferred package/name identity. Validate mount/root and filter length before work.
2. Establish a native registry-state boundary with proven engine-specific synchronization. Either capture an immutable, bounded set under a registry mechanism that guarantees a consistent view, or use a verified generation/event protocol that cannot miss, reorder or race relevant changes during enumeration and validates that generation at publication. Do not assume that registering callbacks or comparing counts is sufficient. If atomic capture/index readiness cannot be established, explicitly refuse or return a separately named partial result with its limitation; never report a complete snapshot.
3. Enforce native caps during collection, before unbounded allocation: maximum scanned rows, accepted rows, elapsed work, total encoded bytes, object-path and class-path lengths, retained snapshots and lifetime. Use an engine-supported bounded iterator or a separately maintained bounded index only after verifying its guarantees. Abort or return an explicitly incomplete outcome on caps or registry-not-ready conditions. Do not claim a bounded total operation if the underlying API first builds an unbounded array. If safe incremental processing requires multiple editor ticks, preserve game-thread ownership, a bounded deadline and an honest cancellation/outstanding-work contract.
4. Store only the bounded immutable snapshot under a host-generated, unguessable handle bound to the attested editor process epoch, exact project, query, and immutable snapshot identity. Bound handle count, memory and expiry; reject foreign, expired, malformed and cross-epoch handles. This handle is a local correlation token, not proof of an authenticated MCP user or a cross-process lock. Do not treat the shared HTTP authority as per-client identity.
5. Page the frozen set with strict page-size and serialized-byte bounds. A continuation is scoped to its exact snapshot and cursor position, with consistent filter identity and explicit `hasMore`. Refuse malformed, wrong-query, expired and stale handles rather than falling back to an offset. Once the snapshot is admitted, later registry changes may leave the snapshot historically valid but cannot turn it into evidence of current asset state; report its capture epoch/generation and revalidate each later use. Explicitly bound output and validate every native response, with no generic file access or arbitrary provider escape.
6. Retain or close snapshots through an explicit bounded lifecycle; shutdown releases only host-owned memory resources, not native editor sessions or unrelated resources. On transport failure after dispatch, fence outstanding work under the existing queue contract; no automatic replay or reset.

If the selected engine does not offer a provably bounded consistent view or reliable generation boundary, defer this exact snapshot contract and consider a separately named best-effort listing with strictly disclosed completeness and fresh per-item readback, subject to a separate selection decision. A best-effort route cannot satisfy CAP-01's exact discovery completion gate by relabeling a cursor as a revision.

## Verification and promotion gates

Before catalog promotion, compare exact candidates, their component licenses and pinned source/patch hashes; establish a live marker and loaded native build provenance for any compatibility delta. Fixture cases must cover duplicate asset names in different packages, multiple objects in a package, unusual object paths, duplicate identities, registry not yet indexed, empty roots, missing or inaccessible mounts, overlarge collections and strings, cap/deadline refusal, response byte caps, no-partial-as-complete behavior, wrong filters and editor epochs, malformed/expired/cross-project handles, and no unbounded folder/metadata side channel.

Exercise adds, removals, moves and same-count substitutions on both sides of a page boundary during capture and after publication; verify all observed results conform to the selected snapshot or fail closed. Test process restart, concurrent clients within shared authority, explicit release, timeout and late completion without replay. Fixture results only establish protocol behavior. Native acceptance must additionally use the exact loaded build, engine version, project, source revision, patch and profile; inspect actual asset identities and registry/index state, and reproduce the race cases against a disposable project. The selected project and editor are currently not supplied, so that acceptance remains blocked.
