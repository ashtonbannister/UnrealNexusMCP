## Vehicle candidate: placed-actor configuration

EngineWire's [canonical registry](https://github.com/ChiR24/Unreal_mcp/blob/5a17d6d343ef9b40a509068cff73f1bfb4509815/src/tools/catalog/capabilities/generated/canonical-registry.generated.json) describes `animation_physics.configure_vehicle` for a placed skeletal-mesh actor. Its input requires `actorName`; optional `vehicleType` is `WheeledVehicle4W` or `WheeledVehicle`, with `mass`, `dragCoefficient`, `wheels` (bone, offset, radius, width, friction), engine (`maxRPM`, `maxTorque`, `gears`) and transmission (`finalDrive`, `finalDriveRatio`, `gearRatios`). The registry states `ChaosVehiclesPlugin` and `EditorScriptingUtilities`, editor state `edit`, write and non-idempotent; the level must be saved separately. These are source-declared prerequisites, not proof of a particular engine version or loaded plugin.

The [native wheel/engine helper](https://github.com/ChiR24/Unreal_mcp/blob/5a17d6d343ef9b40a509068cff73f1bfb4509815/plugins/EngineWire/Source/EngineWire/Private/Domains/Animation/Physics/McpAnimVehiclePayload.cpp#L5-L175) clears the existing wheel setup array before filling it, skips non-object elements, increments `ConfiguredWheels` even if reflective property writes fail, and ignores several numeric setter results. A success receipt or count cannot prove every requested property was applied. `actorName` is not, by itself, a demonstrated exact world-qualified identity. Distinguish a placed actor's level persistence from changing a vehicle Blueprint asset or claiming calibrated suspension/physics.

**Proposed child V-01 — exact placed-vehicle configuration and readback** (owner: vehicle adapter maintainer; priority after CAP-01): compare exact actor/world identity and native property schemas across candidates, require capability/version checks and read back every requested wheel, engine, transmission and mass field; surface per-field refusal and partial mutation. Examine destructive wheel replacement and recovery before routing. Fixture cases: duplicate labels, wrong world, missing property/type, invalid wheel entry, partial reflected writes, existing component and save failure. Native qualification: actual property readback, explicit level save/reopen, then observed PIE steering, throttle, braking and suspension on an identified build. No calibrated dynamics claim follows from these observations alone.

## Audio candidates: editor preview, positional event and managed playback

UE-MCP's [audio category](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/audio.ts#L20-L35) exposes `play_at_location` and `spawn_ambient`; their [generated input descriptions](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/specs/audio.generated.ts#L1695-L1718) document sound path aliases, optional location and volume; the positional event additionally accepts pitch, while ambient spawn accepts label and conflict policy. The [native play handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Audio/AudioHandlers.cpp#L621-L653) loads `USoundBase`, selects the editor world and calls `PlaySoundAtLocation`. It reports the asset and no rollback; it does not provide an owned playback handle or an independent measured-output proof. A timeout cannot justify replaying the one-shot. The [ambient handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Audio/AudioHandlers.cpp#L655-L709) spawns an editor-world actor, performs label-conflict handling, sets a sound component and returns a label-based inverse; it is not the same contract as an ephemeral one-shot or an exact-path owned session. Explicit level save and reload evidence are still required for persistence claims.

EngineWire's pinned registry describes `system_control.play_sound` as an editor-only 2D preview and `manage_audio.play_sound` with required `action`, `playback`, `soundPath`, with distinct 2D, location, spawn, attachment, prime and measurement forms; `manage_audio.stop_sound` includes a broad `all` mode affecting editor and game sounds. Do not equate 2D preview, positional playback, managed handle, measured signal and stop-all. Its registry declares no extra required plugin for these rows; [UE-MCP's build dependencies](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/UE_MCP_Bridge.Build.cs#L45-L60) include AudioEditor and AudioMixer. Device routing, sound attenuation, editor/game mixing and actual output depend on the selected runtime and remain unknown.

**Proposed child A-01 — exact editor one-shot event** (owner: audio adapter maintainer; priority after CAP-01): require explicit sound asset, editor-world identity and finite bounded spatial/gain arguments; preserve no-rollback and uncertain-outcome fencing. Fixture wrong target, missing sound, malformed receipt and post-dispatch loss. Native case must observe the intended output path independently; an acknowledged call is not evidence of an audible sound.

**Proposed child A-02 — owned managed playback** (owner: audio/session maintainer; priority after CAP-02): compare 2D, spatial and attached playback separately; define ownership, returned handle, exact stop and interruption/restart cleanup before selecting a route. Refuse broad stop-all as a substitute for owned cleanup. Test concurrent clients, looping playback, absent/stale handles, target mismatch and unconfirmed stop. The upstream registry's `measure` description is not proof of physical loudness at a listener.

**Proposed child A-03 — ambient actor persistence** (owner: world/audio maintainer; priority after CAP-01): specify exact actor identity, component sound readback, conflict outcomes and explicit level save/reopen. Test duplicate labels, missing sound, component failure and partial save. Do not equate a label-based delete descriptor with a proven safe inverse.

## Effects candidates: asset authoring, compile and world spawn

UE-MCP's [Niagara category](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/niagara.ts#L32-L55) exposes create, compile and spawn as separate actions. The generated [parameter summary](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/specs/niagara.generated.ts#L1568-L1609) describes `create(name, packagePath?, onConflict?)`, `compile(systemPath, force?, includeGpuShaders?)` and `spawn(systemPath, location?, rotation?, label?, scaleX?, scaleY?, scaleZ?, autoDestroy?)`. The [creation handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Niagara/NiagaraHandlers.cpp#L564-L593) uses an idempotent asset creation helper and records checked save outcome; inspect an existing-object return and failed save separately from creation. The [compile handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Niagara/NiagaraHandlers_Compile.cpp#L165-L230) requires editor-only data and waits for compilation before gathering script results; exact status, diagnostic, GPU and persistence guarantees still require end-to-end inspection and fixture validation. The [spawn handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Niagara/NiagaraHandlers.cpp#L725-L805) uses the editor world, creates its own actor host, activates its component and returns its actor path; component activation does not prove particles rendered, and save/reload is a separate operation.

EngineWire's registry describes `manage_effect.edit_niagara_system` with an `edit` selector and optional `save`; its `spawn_niagara` describes a PIE-world-first/editor fallback and an unsaved actor. Those targets are not equivalent to UE's explicit editor-world handler, nor is an edit receipt equivalent to compile or observed runtime output. The pinned UE [plugin descriptor](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/UE_MCP_Bridge.uplugin#L58-L64) names Niagara; EngineWire's registry also lists Niagara. Exact engine/plugin version and support remain to be established.

**Proposed child FX-01 — exact effect asset creation** (owner: effects authoring maintainer; priority after CAP-01): compare exact destination, asset type, conflict/overwrite, dirty and checked-save behavior, and per-item partial results. Fixture existing destination, wrong class, failed save, stale identity and no-op; native verify file, asset readback and reload.

**Proposed child FX-02 — compile diagnostics** (owner: effects compiler maintainer; priority after FX-01): bind exact asset/build, expose scoped compile options and preserve each script diagnostic and status; distinguish warning, error, skipped data, pending compile, GPU limitation and save. Fixture invalid script, partial diagnostics, late timeout and no automatic replay. Native qualification requires a known valid and broken system and actual matching compile results.

**Proposed child FX-03 — exact-world activation and observation** (owner: effects runtime maintainer; priority after CAP-01 and FX-02): select exact editor or PIE world/client without PIE-first fallback, preserve returned host identity and owned cleanup. Test duplicate labels, wrong world, missing asset, activation failure and lost completion. Native observation must verify the selected scene rendered or emitted as intended, with a defined observation method and separate persistence evidence.
