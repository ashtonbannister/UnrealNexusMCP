## CAP-09: material instances versus material graph edits

The existing selected persisted instance route is not a general material-graph authoring API. At Hayba `b69ed11011f89aed3c444a50bd2331b99551c777`, [native `MatSetParam`](https://github.com/zajalist/hayba/blob/b69ed11011f89aed3c444a50bd2331b99551c777/unreal/HaybaMCPToolkit/Source/HaybaMCPToolkit/Private/handlers/HaybaMCPMaterialHandler.cpp#L1326-L1460) loads an existing `UMaterialInstanceConstant`, refuses a read-only package, checks the named scalar/vector/texture parameter, modifies and reads it back, then attempts persistence. Its return includes `verified`, `saved`, `dirty`, and a save error when relevant. A false save is not rollback of the already modified instance. Native code also contains a boolean static-switch branch, but the pinned [public TypeScript schema](https://github.com/zajalist/hayba/blob/b69ed11011f89aed3c444a50bd2331b99551c777/mcp-tools/hayba-mcp/src/tools/material/material-set-param.ts#L13-L23) accepts only number, array, or string. Its 1–4 vector schema differs from the native 3–4 requirement. Do not route a boolean through that surface, or expand the existing strict scalar/vector/texture contracts by analogy.

Claireon `89bee2f4c62d1df625cca71ae66e7c81a415a009` instead offers a candidate material delta: [its phase implementation](https://github.com/believer-oss/Claireon/blob/89bee2f4c62d1df625cca71ae66e7c81a415a009/Source/Claireon/Private/Tools/FClaireonDeltaApplicator_Material.cpp#L80-L200) opens/reuses a material session and can disconnect inputs and delete expressions. That is a different target and mutation scope from updating an instance parameter. Its session and connection semantics are not yet a selected canonical graph contract. A future child contract must distinguish asset/session identity, expression and pin identity, default/override/layer association, graph dirty state, compilation diagnostics, and explicit save/readback. Creating an asset, creating a node, connecting an edge, editing a value, compiling and saving are separately observable effects; do not infer any from another.

**Fixture/native evidence required:** exact material and parameter identities; missing/wrong-type names, finite and float32-representable values, invalid vector size, missing texture and read-only package before mutation; actual observed value and per-package save receipt; failed save after successful in-memory edit; explicit disk hash and reload when persistence is claimed. For graph children, add ambiguous/stale expression/pin, disconnect/delete followed by failure, compiler errors/warnings, asset collision and save failure. Preserve all diagnostics and partial effects. Native compile/reload and actual parameter behavior remain unrun.

## CAP-10: declarative widget spec versus granular or live widget actions

The pinned Claireon [widget spec applicator](https://github.com/believer-oss/Claireon/blob/89bee2f4c62d1df625cca71ae66e7c81a415a009/Source/Claireon/Private/Tools/ClaireonSpecApplicator_WidgetBP.cpp#L317-L492) records a failed widget-class lookup or creation and continues to other entries. Its later wiring pass warns and continues when a parent is absent or is not a panel. In the inspected slot-property loop it invokes `WriteSlotProperty` without testing its boolean return; widget-property write errors become warnings. Therefore a completed spec call does not alone establish every property or relationship, and an adapter must retain per-entry status and warnings rather than convert the overall reply into a complete tree claim.

The same revision's [shared spec driver](https://github.com/believer-oss/Claireon/blob/89bee2f4c62d1df625cca71ae66e7c81a415a009/Source/Claireon/Private/Tools/FClaireonSpecApplicatorBase.cpp#L121-L207) turns compile and save failures into warnings and then returns its success result. Its dry-run branch calls `UndoTransaction`; source comments asserting disk or state outcomes do not replace independent rollback evidence. Asset tree inspection, extracting a subtree, creating/reparenting one widget, writing one typed property, compiling/saving the Widget Blueprint, and interacting with a live widget have different identities, persistence and world effects. None is selected by this review.

**Fixture/native evidence required:** duplicate/ambiguous widget names, exact asset and tree identities, failed class or parent resolution, non-panel parent, invalid nested or typed slot/property values, per-entry success/failure and resulting tree readback. Separate compile failure, save failure, resulting dirty state and disk/reload evidence; a live interaction claim additionally needs an identified runtime instance, visible effect and cleanup. Record what was not applied, not just what was requested.

## CAP-11: retain the atomicity hold

Claireon's [delta driver](https://github.com/believer-oss/Claireon/blob/89bee2f4c62d1df625cca71ae66e7c81a415a009/Source/Claireon/Private/Tools/FClaireonDeltaApplicatorBase.cpp#L190-L270) validates, opens a session and transaction, then runs disconnect, remove, create and connect phases. A phase failure calls phase cleanup, cancels the transaction, closes an owned session and returns an error. Material [failure cleanup](https://github.com/believer-oss/Claireon/blob/89bee2f4c62d1df625cca71ae66e7c81a415a009/Source/Claireon/Private/Tools/FClaireonDeltaApplicator_Material.cpp#L350-L393) removes newly created expressions. The reviewed code does not itself establish restoration of already removed expressions or disconnected links. Transaction cancellation, cleanup or an undo call is therefore insufficient evidence for an atomic contract; this is a source-based qualification gap, not proof that every native run leaves damage.

**Acceptance experiment:** in a disposable revisioned project, snapshot the graph/tree, package dirty flags, asset registry, disk bytes and undo history; perform valid mutation A, then fail B after a disconnect or deletion. Compare all snapshots and record surviving effects and owned-session cleanup. Repeat for property, compile and save failure and, where relevant, new assets and pre-existing links. Distinguish native error receipts from actual restoration; retain source and artifact hashes, engine/editor identity and exact operation. If restoration is not independently proven for a specific family and failure path, expose at most an honest, separately reviewed partial-result contract with recovery instructions; do not label it atomic.
