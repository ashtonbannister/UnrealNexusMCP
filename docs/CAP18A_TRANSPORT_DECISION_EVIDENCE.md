# CAP-18A transport decision evidence

Status: **source and documentation review only; neither transport is selected, implemented, or qualified**. The callable `screenshot.pie` operation remains held. This note refines the open dependency and Windows API questions in the [transport review](CAP18A_SOURCE_TRANSPORT.md) and [image contract](CAP18A_IMAGE_CONTRACT.md). No response-size budget, source patch, or live behavior is asserted.

## Pinned WebSocket client default

The locked UE-MCP revision `62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d` [package lock](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/package-lock.json) records `ws` **8.22.0**. At that same pin, the [bridge constructor](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/bridge/bridge.ts#L688-L700) does not set `maxPayload` in its `WebSocket` options. The versioned [`ws` client documentation](https://github.com/websockets/ws/blob/8.22.0/doc/ws.md) and [implementation](https://github.com/websockets/ws/blob/8.22.0/lib/websocket.js) specify a default of **100 MiB per message**; the versioned [receiver](https://github.com/websockets/ws/blob/8.22.0/lib/receiver.js) also compares its accumulated decompressed message length to that limit. This is a library-level receiver limit for a server response, not the native bridge's 64 MiB inbound request limit, a proof of low memory use, or a safe image budget.

The bridge [converts a received frame to text and parses the full JSON before pending-ID matching](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/bridge/bridge.ts#L1017-L1062). A candidate direct-byte-over-JSON design must therefore enforce a smaller explicit frame bound at this receiver *before* allocation/parse, a native encoded-byte and pixel bound before response creation, and separate limits for JSON, base64 expansion, decoded PNG and MCP delivery. The default maximum may allocate far beyond an acceptable screenshot budget and library version/actual runtime installation must be verified separately. Do not derive an outbound application limit from the unrelated native inbound cap. The pinned library's `perMessageDeflate` client default is enabled; negotiated compression and its resource impact must be measured and tested rather than assumed away.

## Windows path ownership is not resolved by `CREATE_NEW`

Microsoft's [CreateFileW contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) documents `CREATE_NEW` collision failure, sharing and final symbolic-link behavior. This does not by itself authenticate how the containing directory was reached, establish its owner or ACL, rule out ancestor redirection, or correlate two later pathname opens. The pinned UE handler instead uses a separate existence test and path-based write. An operator grant or a post-write `overwrote` field therefore cannot establish an authorized physical destination. Keep the route held.

Microsoft documents directory-relative names through `OBJECT_ATTRIBUTES.RootDirectory` in [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) and defines `OBJ_DONT_REPARSE` in the general [OBJECT_ATTRIBUTES contract](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes). However, the user-mode NtCreateFile parameter description specifically names zero and `OBJ_CASE_INSENSITIVE` for that field and does not itself establish the complete combination or a concurrent parent reparse-transition guarantee. `FILE_OPEN_REPARSE_POINT` opens the final reparse point rather than following it; it is not a substitute for verified acquisition of every relevant ancestor. These documented pieces do not alone establish that a native handle-relative lease is safe across the target OS, filesystem, filter drivers and concurrent changes.

A file-lease implementation must independently establish and retain the authorized parent handle, reject unsupported filesystem/reparse states, establish access and share-mode behavior, safely bind the producer and consumer handles to the same file and ensure identity-safe release; the [lease design](CAP18A_IMAGE_CONTRACT.md) states these as requirements, not existing capabilities. A future implementation must support each security-critical API combination on its exact Windows/filesystem lane and fail closed when the required boundary cannot be demonstrated. The `CREATE_NEW` final-name protection is useful but is not a complete namespace authorization proof.

## Remaining decision and validation

Direct bytes and a protected file lease are materially different contracts. Direct bytes avoid a temporary-file lifecycle but require an explicit bounded bridge/MCP protocol and exact-world correlation. The file lease needs an independently authorized root, native handle semantics, ownership, cleanup and reparse-race evidence. Neither may be used as a silent fallback for the other. Selecting one requires the project's architecture decision, reviewed fixed schema and immutable compatibility patch, plus fixture and live evidence. Both approaches still require actual loaded-binary provenance, selected PIE context, no-replay handling, scoped image decoding and LIVE-03 acceptance. No evidence in this note establishes a safe implementation or allows the held path to run.
