# CAP-01: exact-world actor discovery source review

Status: **source comparison only**. No new canonical operation, provider winner, compatibility patch or native qualification is established. CAP-01 remains incomplete. Existing exact actor inspection routes are unchanged. This review examines current pinned provider behavior; source analysis cannot prove the loaded native build, engine behavior or actual object lifetime.

## UE-MCP: outliner candidate

The [pinned `get_world_outliner` handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Level/LevelHandlers.cpp#L899-L1067) accepts world, PIE instance, filters, cursor and limit. It returns `Actor->GetPathName()` separately from label and name; a label collision alone is therefore not a reason to discard a row. Its default excludes `LandscapeStreamingProxy` and `WorldPartitionHLOD`, recording `streamingSkipped`, and the iterator observes loaded actors, not necessarily every unloaded World Partition actor.

A page limit does not bound the native collection: the handler walks the world actor iterator, builds every matched row including every actor's component array, sorts the rows and only then emits the requested page. Long strings, large component counts and broad worlds can create unbounded intermediate work and response preparation. The page request's query binding includes the world scope and filters but **not `pieInstance`**. A cursor is consequently not explicitly bound to an exact PIE instance by that query. The response reports `worldName`, not an attested object path plus process/editor epoch. Follow-on reads require their own exact identity checks; discovery is not a lock.

The pinned [world resolver](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Public/HandlerWorld.h#L75-L136) selects the first matching PIE or game context, rounds numeric instance inputs, and resolves unrecognized scope strings to the editor world. A gateway's strict schema can disallow unknown scopes and noninteger inputs, but cannot prove native context uniqueness or fix a cursor shared across instances. Whether duplicate PIE instance identifiers are possible on a target engine remains unverified; it must not be assumed impossible as a proof of uniqueness.

## Existing exact actor inspection: receipt limitation

The selected `actor.inspect.editor` and `actor.inspect.pie` routes fix the world selector and, for PIE, require an integer instance and full actor path. The [pinned actor-detail handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Level/LevelHandlers.cpp#L1355-L1478) selects a world and resolves the actor within it, but its success object reports `actorPath` and does **not** report the resolved world or PIE instance. The [world resolver](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Public/HandlerWorld.h#L75-L136) matches the requested instance when selecting a PIE/game context. The [path resolver](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Public/HandlerActorResolve.h#L64-L80) searches actors in that world. The [outer dispatcher](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/dispatch/server-dispatch.ts#L175-L190) may append editor attribution; its [result shaping](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/dispatch/server-dispatch.ts#L480-L483) does not supply resolved PIE-world attribution.

Nexus forwards the received result and does not establish a returned-world or returned-instance postcondition. An editor process attestation, echoed request or PIE-looking path is not a native resolved-world receipt. The current catalog postconditions remain requirements, not demonstrated receipt guarantees. Compare the returned path and obtain independent world/instance corroboration; do not invent verification from the requested selector. A reviewed native compatibility change can report the actual world context and PIE instance with an independently verified live marker, followed by source/fixture and live qualification. This source gap does not itself demonstrate that a real call selected the wrong world. Native actor-path reuse and unbounded component enumeration also remain separate limitations.

## EngineWire: actor list candidate

The [pinned `control_actor.list` handler](https://github.com/ChiR24/Unreal_mcp/blob/5a17d6d343ef9b40a509068cff73f1bfb4509815/plugins/EngineWire/Source/EngineWire/Private/Domains/ControlActor/List/McpActorList.cpp#L39-L241) automatically uses `GEditor->PlayWorld` when set and otherwise the editor world. It does not expose an exact world or client selector in that handler. It gathers all actors before page slicing, reports an offset continuation without a stable snapshot, and the editor-world source uses `GetAllLevelActors`, which excludes several categories that the handler reports through an aggregate excluded count. Its rows include object paths and class paths; those facts do not make it an exact-client or bounded snapshot contract. Current-viewport and first-play-world semantics must not be treated as the requested exact PIE-client variant.

Neither reviewed implementation meets CAP-01's complete bounded discovery and exact-world requirements as-is. Do not add either to the executable allowlist solely from this comparison. Other pinned provider candidates still require review; these findings do not assert that no alternative exists.

## Narrow patch and admission requirements

A possible child contract is a single bounded snapshot of **loaded** actors in a specifically selected editor world or explicit PIE instance. It must not claim unloaded World Partition coverage. Require validated scope and integer instance, reject multiple or missing matching world contexts, and return exact world identity plus an editor process epoch established by the host. Preserve distinct paths even with duplicate labels. The engine must expose enough identity to distinguish deletion/recreation; where that identity cannot be established, explicitly refuse instead of treating object path reuse as a durable actor identity.

Enforce bounds **while traversing**, before building large arrays: maximum visited actors, selected rows, string lengths and actual encoded bytes. Omit component enumeration unless separately bounded. If a traversal or byte/time cap is reached, return an explicitly incomplete result with no completeness claim. A one-response snapshot avoids mixing pages but does not authorize a later write: native consumers must re-resolve and validate identity and any revision precondition at the actual mutation boundary. If a future multi-page contract is needed, use a bounded immutable snapshot bound to exact project, world, epoch and query; malformed, foreign, expired or cross-instance continuations must refuse without offset fallback. A process-local handle is correlation, not authenticated user identity or a global editor lock.

Any implementation must preserve the existing public-surface restrictions, source hash/compatibility marker checks, unknown-outcome fence and no replay/failover policy. Native scheduling and editor callbacks can change actors; prove snapshot semantics on the supported engine rather than assuming a single game-thread callback is an atomic global lock. Native build and loaded-artifact evidence remain required before qualification.

Fixture acceptance should exercise duplicate labels, exact paths and reused paths, unknown scopes, fractional/missing/multiple PIE selectors, cross-instance continuations, world teardown/restart, concurrent adds/removes, cap overflow and oversized fields. Verify no partial result is reported complete, no unloaded-world claim is made, and no transport loss causes retry. Native acceptance additionally observes the selected engine, project, loaded build, PIE client and direct-client interference with captured receipts and explicit recovery. These are acceptance requirements, not test results.
