# CAP-18A — exact PIE image delivery design

Status: **direct bounded bytes selected by the owner on 2026-10-28; not implemented or qualified**. This document narrows the [CAP-18A task](CAPABILITY_BACKLOG.md#cap-18a) and its [pinned-source investigation](CAP_PREREQUISITES_RESEARCH.md#cap-18a-selected-pie-image-delivery). It does not select a new executable route, modify the lock, assert a secure implementation, or qualify a native editor. FIX-01 and FIX-02 remain integration prerequisites. The first proposed platform is the Windows x64 interactive lane; other platforms need separately reviewed OS implementations.

## Observed baseline and exact scope

The selected `screenshot.pie` is a capture-to-file operation. At UE-MCP pin `62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d`, the [handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Editor/EditorHandlers.cpp#L2822-L3064) selects a PIE world and its game viewport, uses synchronous Slate capture, encodes a PNG, then checks whether the filename exists separately from writing it. Its receipt contains the actual target, dimensions and selected world/PIE instance when available; it can overwrite a previous file. The existing success response is not a freshness or exclusive-ownership proof. A selected viewport can include UMG/Slate, while the debug canvas depends on engine flags; no full-window or physical-input claim follows. A current-view EngineWire image remains a distinct contract.

Proposed child contract: **one explicitly selected PIE instance and exact world path, one capture, one returned MCP `image/png` block**, plus the unmodified native receipt and warnings. The native selected world path and instance must exactly match the call and its active editor epoch. Missing, ambiguous or mismatched target, headless/no capturable widget, interrupted response, or inconsistent receipt is an error; no fallback to an editor viewport, another PIE client or a prior image. Re-attest the editor/project and epoch through the existing provider boundary before dispatch; receipt correlation does not replace loaded-binary identity. Distinguish receipt, actual bytes, observed pixels and independent client/gameplay verification.

The new operation must have a fixed native method and schema, no caller-selected filesystem path or arbitrary file reader. The existing file-writing operation stays separate until an explicitly reviewed migration. The selected direct-byte operation must not create a temporary image file. Describe its actual capture and in-memory effects accurately; a post-dispatch timeout is not rollback. Do not mark it idempotent or retry it automatically after an uncertain dispatch.

## Unselected Windows artifact alternative

The owner selected direct bounded bytes instead of this file-lease approach. This historical alternative is retained for comparison only; it is not an automatic fallback or a requirement of the selected method. It is not implemented by the current transport or Node runtime.

1. The host creates a cryptographically unpredictable, single-use request nonce, bound in memory to the selected project, editor process epoch, exact PIE instance, world path and one pending call. It supplies no user-controlled path. The native patch must expose a versioned capability marker and reviewed source/patch hashes; the live marker is distinct from proof of the loaded module.
2. The operator configures a dedicated local staging directory for the selected runtime, owned and writable only by the trusted service/editor identities. Before enabling the capability, validate the complete parent chain and its ACL/ownership and reject untrusted writable or reparse-point ancestors, remote/network filesystems, and missing required Win32 handle semantics. A string-prefix or `realpath` check alone does not secure a later path-based open. Directory provisioning and its exact ACL, traversal permissions, and behavior against other same-user processes require a reviewed Windows implementation and integration tests; no claim of protection against another process with equivalent privilege is implied.
3. The patch captures the requested viewport, validates pixel dimensions and checked multiplication **before** allocating/encoding, then encodes PNG under explicit reviewed byte, pixel and time budgets. It creates a fresh opaque basename under the protected directory using Win32 `CreateFileW` with `CREATE_NEW`, `FILE_FLAG_OPEN_REPARSE_POINT`, and producer sharing that permits readers but denies new write and delete opens while the producer retains the handle. The precise desired-access and bidirectional share flags must be tested: a reader must also share the producer handle's existing write access while its own desired access remains read-only. The temporary file is newly created, not a pre-existing path, and the operation must fail on collision. It writes completely, verifies the final length and hash, and keeps the handle open through handoff. Native limits must be applied before a large WebSocket/JSON response can be constructed. The exact limits are configuration/contract values to be selected from measurements, not invented here.
4. The patch returns a bounded receipt containing protocol version, nonce, exact world and instance, project/editor epoch evidence, dimensions, PNG byte count and digest, opaque basename and handle-derived file identity. It must not provide an unvalidated caller-chosen absolute path. The Windows reader opens only that basename relative to the verified staging root, with no reparse traversal, read-only desired access and a share mode compatible with the producer's existing handle; compare volume and file identity from the two **simultaneously open handles**, size and digest. Both handles remain held through the read so path substitution, rename, deletion or write by incompatible opens cannot silently change the object. The adapter must use a reviewed OS-native handle API; Node pathname helpers alone are not sufficient. If the required handle-relative opening or trusted-root guarantee cannot be implemented, the capability stays disabled. File IDs alone are not timeless proof: filesystems may reuse identifiers after handles close.
5. The adapter reads a bounded number of bytes from that same verified handle, checks exact advertised length and digest, PNG signature, complete well-formed PNG/chunk checksums, one valid IHDR, decoded dimensions and pixel/decompression bounds, and that dimensions match the native receipt. Decode with bounded library behavior or an isolated bounded decoder; merely reading IHDR does not prove a safe complete image. Preserve the native receipt, warnings, partial details and metadata; add an MCP `image/png` block only after validation. Response-size limits must account for binary-to-base64 expansion and the whole MCP/bridge frame; check transport limits at each layer and fail rather than truncate or silently transcode.
6. A private, fixed host-to-native release message correlates the nonce and lease. It is not a public model-callable path/delete API. On successful read or explicit abandonment, close the adapter handle, then have the producer close/delete the owned temporary artifact by an already-held handle or equivalent tested identity-safe mechanism. Record cleanup confirmation separately. A timeout, process crash, lost release or cleanup error retains an **unresolved** artifact/lease record; bounded shutdown reports incomplete cleanup and never deletes by an untrusted path. Establish an operator-owned reconciliation procedure for stale leases; do not automatically delete a replacement or unrelated file. If synchronous handler execution prevents retaining a lease safely or a private release cannot be isolated, this protocol must not be shipped without a separately reviewed transport design.

`CREATE_NEW` and sharing flags must be verified against the actual target filesystem, Windows version and identity/ACL model. Microsoft documents [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) creation and sharing semantics and [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) for comparing open handles. The final component flag does not itself validate every ancestor. These APIs establish pieces of the design, not proof that the end-to-end protocol is safe.

## Selected direct-byte direction

A separately versioned native handler is intended to return bounded PNG bytes directly in a correlated response, avoiding temporary image files and pathname races. The [direct-byte patch plan](CAP18A_DIRECT_PATCH_PLAN.md) records the remaining capture primitive, native identity, bridge framing, base64, memory, concurrency, metadata and live-qualification gates. Selection does not implement or qualify the operation, lift the existing file-route hold, or authorize fallback to it.

## State, failure and acceptance

For the selected direct-byte direction, distinguish request preparation, dispatch, verified delivery and an unknown post-dispatch outcome. Do not assume cancellation or retry is safe. For the unselected file-lease alternative, the proposed request/lease states are `prepared`, `dispatched`, `capture_complete`, `opened_and_verified`, `delivered`, and `released`; `unknown` and `cleanup_unconfirmed` are durable local reporting states, not automatic retry or cleanup commands. A post-dispatch timeout, cancellation, malformed receipt or lost connection fences shared editor execution under the existing queue rules. The native editor could still be capturing. A validation failure after a confirmed native capture reports an image-delivery failure while preserving the receipt; it cannot fabricate a valid image. If completion itself is uncertain, preserve the uncertainty fence. A capture success does not prove client display, game correctness, or durable persistence; cleanup of any owned resources must be reported separately.

Before exposing the operation, record source comparison and license, exact immutable patch and hash, native build/loaded marker verification, capability probe, canonical schema/fixed route, workflow guidance, optional-pack behavior, and rollback/reconciliation instructions. The patch must retain upstream notices and not alter existing screenshot semantics silently. Removing or disabling the new route is an operator action after reconciling outstanding captures; it must not automatically replay the original request or delete uncertain artifacts.

Fixture and native acceptance must independently cover:

- Correct requested client and exact world in multi-client PIE, including duplicate/mismatched and absent targets; no fallback and no second dispatch.
- For the unselected file-lease alternative only: pre-existing file/collision, relative or traversal input, altered project root, symlink/junction/reparse ancestors and final component, unauthorized directories, and attempted replacement before/during read.
- Reused nonce, stale receipt, changed editor epoch, mismatched size/hash/dimensions, duplicate response, malformed/truncated PNG, decompression bomb and over-limit capture/frame.
- Capture, encoding and delivery failures; file create, write, flush, read, release and artifact cleanup apply to the unselected alternative; timeouts and cancellation at each boundary; concurrent direct clients and same-user processes within the stated trust boundary.
- Retained original receipt, images, metadata and warnings; shared queue fencing across clients; no arbitrary read, replay, fallback or uncertain deletion; bounded repeated shutdown and explicit unresolved cleanup.
- A real interactive editor with the identified loaded build and client viewport, recognizable test pixels and UI, actual payload bytes/dimensions, controlled failure cases and recovery under LIVE-03. Fixture responses and static source review do not satisfy this row.

Record exact engine/platform, source/patch/build hashes, enabled profile, transport limits and editor epoch. Limit any support statement to that tested combination. The selected direction still needs a bounded capture primitive, per-frame and concurrency limits, shutdown semantics and a transport framing budget. Filesystem, staging, ACL and lease questions apply if the unselected file alternative is reconsidered. Resolve the selected design with implementation and evidence, not assumptions.
