# CAP-01 and CAP-18A: pinned-source prerequisite research

Research against Nexus `ac4640472d62ef40c5ef3b00a156603889f60e92` and the locked UE-MCP revision `62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d`. This is a partial source review, not a candidate selection, executable contract, implementation, or native qualification. The [capability backlog](CAPABILITY_BACKLOG.md) remains the task-state authority. Both families depend on FIX-01 and FIX-02; their native acceptance remains separate.

## CAP-01: discovery and graph read

### Asset listing candidate

At the pinned revision, the UE-MCP [asset category](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/asset.ts#L180-L188) exposes a read `list` backed by `list_assets`. Its [native implementation](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Asset/AssetHandlers.cpp#L1323-L1390) accepts a cursor and limit, rejects row offset, includes the filters in its page request, and sorts the registry results before paging. It sets a default limit of 500 and a maximum of 5000. Pagination bounds the page; the source still materializes and sorts the registry result, so it is not evidence of bounded total server work or a stable snapshot across arbitrary concurrent changes.

A candidate Nexus child contract needs an explicit content root, bounded filters and response size, opaque cursor handling tied to those filters, honest stale-cursor/refusal behavior, and an exact asset identity suitable for a subsequent independent read. Compare other eligible providers and inspect the exact returned row and pagination implementation before selecting a route. Test concurrent registry changes, invalid and mismatched cursors, truncation and empty pages. Verify live behavior separately.

### World and actor discovery candidate

The pinned UE-MCP [level category](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/level.ts#L10-L18) advertises `get_outliner` through `get_world_outliner`. The existing [actor inspection audit](audit/world-assets.md) selects exact-path inspection with an explicit world and distinguishes it from discovery. An outliner description alone does not establish stable world selection, pagination, unloaded World Partition coverage, or uniqueness under duplicate labels. Inspect its pinned native schema and handler, compare candidates, and define editor versus exact PIE-instance enumeration as separate contracts where necessary. A later exact selection must preserve full actor path and world identity, and refuse stale or ambiguous identities; fixture and live cases must exercise duplicate labels, unsupported worlds, and large collections.

### PCG graph read candidate

The pinned [PCG category](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/src/tools/pcg.ts#L10-L19) exposes `read_graph` backed by `read_pcg_graph`. Its [native graph read](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/PCG/PCGHandlers.cpp#L940-L1038) loads the supplied graph path, emits ordinary node names and titles, emits input and output pin labels for the implicit graph input/output nodes, and enumerates existing edges with endpoint names and pin labels. At this pin, the ordinary node records in this handler do **not** enumerate all their pins. Existing edges also cannot reveal unconnected pins.

This handler does not expose a node GUID or graph revision in the reviewed output and has no pagination in the reviewed graph traversal. Names and labels therefore do not alone establish stable identity after graph reconstruction, or bounded results for an arbitrarily large graph. Review the pinned node-settings read and other providers for complete pin and type discovery; define how duplicate or stale identities are detected, how reads and writes are correlated across intervening edits, and how oversized results fail without implying completeness. A native patch or a narrower contract may be necessary. The richer ordinary-node pin description on a newer upstream revision is not evidence for this pinned build.

## CAP-18A: selected PIE image delivery

The existing `screenshot.pie` operation remains the source-selected capture-to-file route; it is not an image delivery contract. The pinned [UE-MCP screenshot handler](https://github.com/db-lyon/ue-mcp/blob/62bb9a8f4a41b8ce5ff9a0fbbd5fbe0f49a39c7d/plugin/ue_mcp_bridge/Source/UE_MCP_Bridge/Private/Handlers/Editor/EditorHandlers.cpp#L2822-L3064) selects a PIE world by instance and optional world path, captures the selected game viewport including Slate/UMG synchronously, and writes PNG bytes. Relative filenames go under the project Saved/Screenshots directory. The success receipt includes the path, target, dimensions, overwrite status, and selected PIE world/instance when available; write failure returns an error. The [capture audit](audit/testing-observation.md#ue-mcp-selected-pie-frame-with-umg) documents why the EngineWire current-viewport image is a distinct contract.

The handler checks whether a file already exists and then writes it. Those are separate operations: this is not an atomic no-overwrite guarantee and a concurrent writer can race a preflight. The existing canonical schema accepts a caller-supplied safe basename; it does not establish ownership of the created file. A host-generated unpredictable name reduces collisions but does not prove exclusive creation. A production design must resolve the race with a reviewed native exclusive-write or equivalent ownership protocol, or state and enforce an appropriately limited contract without claiming atomic safety.

A reviewed image delivery design must bind to the selected project and the actual capture receipt, verify the reported PIE instance and optional world, validate the expected destination and path ownership, prevent traversal and symlink escapes and replacement races, and read only the specifically owned fresh capture. Validate PNG structure, reported versus actual dimensions, and byte/pixel bounds before returning an MCP image; preserve the original native receipt and any warnings. Do not expose an arbitrary host-file reader. Test stale or pre-existing files, target mismatch, failed writes, oversized or malformed images, path and symlink attacks, replacement during read, and cleanup/ownership boundaries. Those fixtures are not evidence of live selected-client pixels: LIVE-03 remains necessary.
