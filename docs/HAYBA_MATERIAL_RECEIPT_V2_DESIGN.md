# Hayba material receipt v2: source-only design

Status: historical design; the implemented v2 candidate and isolated scalar evidence are recorded in [material v2 qualification](qualification/HAYBA_MATERIAL_V2_20261112.md). This note concerns the selected Hayba material parameter routes at immutable pin `b69ed11011f89aed3c444a50bd2331b99551c777`. The sections below describe the earlier unpatched behavior and proposed boundary. Current executable routing and patch requirements are defined by the [compatibility manifest](../catalog/compatibility-patches.json), [gateway implementation](../src/specialist-adapters.mjs), and linked qualification record.

## Evidence and limitation

The pinned [native material handler](https://github.com/zajalist/hayba/blob/b69ed11011f89aed3c444a50bd2331b99551c777/unreal/HaybaMCPToolkit/Source/HaybaMCPToolkit/Private/handlers/HaybaMCPMaterialHandler.cpp#L1326-L1460) loads `instance_path`, validates the parameter, mutates and reads it back, then saves. The scalar receipt echoes the original JSON double and observed float, but its `verified` result uses the selected engine's default `FMath::IsNearlyEqual` tolerance. The vector receipt gives only `FLinearColor::ToString()` values. The texture receipt gives the requested string and observed object's path, but not the resolved requested texture object's identity. None of these receipts reports the loaded material instance's actual object path. A matching input echo is not independent proof of the loaded target or of the readback comparison.

The pinned [typed TypeScript wrapper](https://github.com/zajalist/hayba/blob/b69ed11011f89aed3c444a50bd2331b99551c777/mcp-tools/hayba-mcp/src/tools/material/material-set-param.ts) delegates to `ueTool`. The existing v1 patch adds a required TypeScript no-retry marker and removes it before native dispatch. That marker corroborates the reviewed transport schema; by itself it does not establish which native Unreal handler or binary is loaded. The existing fixed TCP listener, OS process epoch and read-only project/PID probe remain separate identity evidence, and even a native capability marker would not replace an independently recorded loaded-artifact hash.

## Proposed narrowly scoped v2 boundary

A future reviewed combined delta should introduce a **distinct, versioned fixed typed operation** rather than silently changing the v1 semantics or widening `hayba_invoke`. It must preserve no-replay behavior on transport loss, native read-only guards, parameter-existence validation, original warnings, partial outcomes and explicit disk-save receipts. It must not auto-retry, fail over or silently fall back to v1 after a lost or ambiguous response. V1 and v2 patch hashes, source-before/source-after hashes and selection must remain explicit; do not infer compatibility from version ordering.

1. **Target before mutation.** Define the input as an exact canonical material-instance object path, obtained from separately reviewed discovery or explicitly supplied by the operator. After resolving it and before `MIC->Modify()`, the native handler must compare the resolved object's full path and expected class/package identity with that exact target and refuse ambiguity, redirection or mismatch. Return the requested and actual canonical identity and the comparison result, while recognizing that paths alone do not prevent deletion/recreation or direct-client interference. A caller-supplied alias or redirect is not proof that the intended object was changed. Where atomic identity/revision cannot be established, remain held.
2. **Typed scalar/vector evidence.** Capture the actual received JSON numeric values and the float32 values the native setter will use, including the default alpha for the three-component vector. A stable representation such as fixed-width hexadecimal IEEE-754 binary32 bit patterns avoids reliance on `FLinearColor::ToString()` decimal precision. Report expected and readback components in that representation, a versioned comparison rule, the actual explicitly supplied finite tolerance and the native readback/verification result. A reviewed implementation must either preserve the original engine comparison and report its exact effective tolerance with evidence, or define a new explicit comparison without treating it as equivalent to the old default. It must reject nonfinite/out-of-float32-range inputs before mutation and handle signed zero and overflow consistently across the actual JSON wire and engine build. The host must verify the request echo and every typed field; an uncorrelated or contradictory post-dispatch receipt is outcome-unknown, not permission to retry.
3. **Typed texture evidence.** Before mutation, resolve the requested texture and compare its actual canonical object identity with an explicitly selected exact target. Report both resolved requested and observed object paths plus the native pointer-equality result. Do not derive identity by splitting strings, or assume redirector/alias semantics from an input path. Mismatch or inability to verify the exact target must refuse before mutation; a contradictory or missing post-dispatch identity must preserve the receipt and fence. Existing source does not establish that arbitrary string equality safely represents every permitted asset alias.
4. **Persistence and partial results.** Keep requested-value echo, readback, native verification, save result, dirty state and any save error distinct. `verified:true` alone is not persistence, and `saved:true` alone is not independently verified disk/reload evidence. If mutation precedes failed verification/save, report the partial state and retain the original receipt. Never report rollback or automatically repeat the setter. Require separately authorized recovery.
5. **Native marker and provenance.** A new TypeScript schema marker can prove only that the direct wrapper advertises the expected fields. Add a fixed, reviewed **read-only native capability probe** or equivalent independently exposed marker that is actually produced by the loaded native handler, and require it together with the direct typed no-retry marker, exact source/patch verification, listener ownership and project/editor epoch before dispatch. Reject absent, malformed, mismatched or unsupported markers; do not infer support from a static descriptor or a TS-only marker. Specify marker shape/version and how it is bound to the actual native listener in the implementation review. Marker presence is not proof of the loaded binary's hash or of an individual mutation outcome.

## Verification and release gates

A source-only patch can be created against the exact pinned checkout, apply-checked in a disposable copy, and accompanied by an immutable manifest covering every changed TypeScript and native file. Focused local fixtures can test fixed-route schema/marker refusal, expected binary32 bit handling including signed zero, malformed or crossed native fields, redirect/mismatched targets, typed comparison discrepancies, partial save/verification failures and retained receipts. Such fixtures can test the Nexus interpreter and a reviewed extracted helper; they **cannot** prove Unreal ABI compatibility, reflected type behavior, actual engine comparison defaults, native game-thread/ownership semantics, loaded artifacts, filesystem persistence or reload.

Native completion requires the selected engine and build, actual patched plugin/server artifact hashes and marker observation, exact project/editor identity, isolated real material instances and textures, direct-client interference checks, pre/post property readback, package save failure and reload evidence. Check the separately required no-retry delta and recovery path on the exact loaded combination. Those were the original exhaustive qualification proposals. The user subsequently requested representative provider read/write checks rather than individual live tests of every command; retain the actual evidence and do not claim unperformed checks passed.
